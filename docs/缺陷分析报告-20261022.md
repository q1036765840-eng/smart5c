## 一、安全漏洞

### 严重

**SEC-01 命令注入 + 任意文件删除 — `LinuxUtil` / `ChmodUtil` 字符串拼接执行 shell**
- 位置：`common/utils/LinuxUtil.java:19,21,37`、`common/utils/ChmodUtil.java:12`
- `Runtime.getRuntime().exec("rm -rf " + filePath)` 与 `chmod -R 777 " + filePath` 直接拼接外部传入的文件路径。调用链可达：`FileUploadServiceImpl.fileDelete`（`FileUploadServiceImpl.java:387-388`）→ Controller `DataUploadController.fileDelete`（`DataUploadController.java:123`，入参 `filePath` 完全由前端控制）。
- 利用场景：传入 `filePath = "/nbk/app/smart5c/data/rawdata/x; rm -rf /"` 或含 shell 元字符的路径，可在服务器执行任意命令；即使不考虑注入，前端可传任意路径删除服务器上任意目录（含系统目录）。
- 修复建议：废弃 `LinuxUtil`/`ChmodUtil`，改用 `Files.walkFileTree` / `Files.delete` 等 NIO API；路径必须规范化后校验在 `inspect.basepath` 之内（`Path.normalize().startsWith(base)`）。

**SEC-02 RSA 私钥硬编码在源码中 + SFTP 口令下发给前端**
- 位置：`common/constants/RSASecret.java:14,19`
- RSA 公私钥对以常量形式提交进仓库，且 `getSftpHostInfo`（`FileUploadServiceImpl.java:339-341`）用该密钥加密 SFTP 账号密码后直接下发给前端——拿到私钥即可解密，等于把 SFTP 口令向所有登录用户（甚至拿到接口路径的任何人）公开。密钥泄露后无法通过换配置轮换（要改代码重发版）。
- 修复建议：私钥移出代码库，放入环境变量或密管系统；`getSftpHostInfo` 接口应做管理员鉴权并评估是否必须下发密码（建议前端直接连 SFTP 时使用一次性 token 或由后端代理传输）。

### 高

**SEC-03 白名单过宽、部分接口未授权可达**
- 位置：`application.yml:55-73`
- `/web/dataUpload/fileUploadCallback` 免鉴权，但同 Controller 下的 `fileDelete`、`addDirectory` 等虽在白名单外，`/upload/product/**`、`/smart5cApi/inspectionData/inspectionDataList`、`/smart5cApi/task/autoCreate` 也免鉴权。配合 SEC-01/SEC-02，未授权者可探测目录树（`getFileCatalogTree`）并删除/新建目录。另外 `/actuator/**`、`/druid/**` 整体放行，生产环境会暴露运行时信息甚至 Druid 监控台。
- 修复建议：白名单收敛到最小集合；actuator/druid 关闭或加独立认证；回调接口加签名/回调 token 校验。

**SEC-04 密码使用 MD5+可逆变换存储**
- 位置：`common/utils/MD5.java:32-56`、`service/Impl/UserInfoServiceImpl.java:239,327`
- 所谓"加盐"实际是对 MD5 结果做 `105 - digit` 的字符替换（`md5MinusSalt` 就是逆运算），无真实盐、无慢哈希，彩虹表变换后可直接碰撞。且登录失败未累加 `loginTimes`/触发 `lockStatus` 锁定（字段存在但登录失败路径未联动）。
- 修复建议：迁移到 BCrypt/Argon2（Hutool `BCrypt` 或 Spring Security Crypto 单包），加密码迁移策略（登录时重哈希）。

**SEC-05 JWT 密钥硬编码且强度不足，无注销撤销机制**
- 位置：`common/utils/JwtTokenUtil.java:19`（密钥 `MDk4ZjZiY2Q0NjIxZDM3M2NhZGU0ZTgzMjYyN2I0ZjY` 提交在源码）；`application-dev.yml:65` 另有 `jwt.secret: smart5c-admin-secret` 实际未被使用（配置与实现脱节）。
- Token 有效期 24 小时，无黑名单/注销；用户被锁定或删除后，已签发 token 在有效期内仍然可用（`AuthenticationFilter.java:142-152` 只查 `account_no` 是否存在，未校验 `lockStatus`/`deleted`——`userInfo` 为 null 时还会 `CurrentUserHolder.set(null)` 后放行，导致 NPE 或越权）。
- 修复建议：密钥入配置中心/环境变量；过滤器校验用户状态；登出接入黑名单或改用短 token + refresh。

**SEC-06 CORS 全开放**
- 位置：`filter/AuthenticationFilter.java:77-80`（`Access-Control-Allow-Origin: *` 且 `Allow-Credentials: true`）、`common/config/GlobalCorsConfig.java`、部分 Controller 上的 `@CrossOrigin`。
- 三处 CORS 配置叠加，`*` + credentials 组合在部分浏览器下被禁止、在其它实现下可导致任意站点携带凭证跨域调用。内网部署风险可控，但公安内网系统仍应白名单化。
- 修复建议：统一在 `GlobalCorsConfig` 中配置 origin 白名单，删除 Filter 内与 `@CrossOrigin` 的重复配置。

**SEC-07 敏感信息进日志/响应**
- 位置：`filter/AuthenticationFilter.java:75,101`（每个请求的完整 Bearer token 打入 info 日志）；`service/Impl/FileUploadServiceImpl.java:339`（SFTP 明文密码组装，若上游调用栈异常会被 log 打出）；`UserInfo` 实体（`entity/UserInfo.java:36`）`password` 字段无 `@JsonIgnore`，登录成功后 `tokenMap.put("userInfo", userInfo)`（`UserInfoServiceImpl.java:277`）把密码哈希返回给前端。
- 修复建议：token 日志脱敏；`UserInfo.password` 加 `@JsonIgnore`；全局日志增加敏感字段过滤。

### 中

**SEC-08 异常堆栈直接返回前端**
- 位置：`common/config/GlobalExceptionHandler.java:44-48`
- `RuntimeException` 统一 `ResultUtil.error(errorMsg)`，`errorMsg` 为异常 message 或**完整堆栈字符串**（`Arrays.toString(e.getStackTrace())`），向客户端泄漏类名、行号、内部实现。
- 修复建议：对外返回通用错误码，堆栈仅入日志。

**SEC-09 Swagger/文档接口生产暴露 + 弱口令**
- 位置：`application.yml:38-41`（`swagger.enabled: true`，账号 `admin`/密码 `123`）且 `/doc.html`、`/v2/api-docs` 免鉴权。攻击者可据此枚举全部接口结构。
- 修复建议：生产 profile 关闭 swagger 或加 IP 白名单，修改弱口令。

**SEC-10 路径穿越风险（文件浏览/删除/解析）**
- 位置：`DataUploadController.java:76,123`、`InspectionDataController.java:198`（`parseData` 接收任意 `filePath` 直接 `new File(filePath)` 解析）
- `getFileCatalogTree`、`fileDelete`、`parseData` 均未把入参限制在 `inspect.basepath` 内，登录用户可浏览/删除/解析服务器任意目录。`fileDelete` 中 `filePath.replace(picturePath, "")` 仅做简单替换，不防 `../`。`fileDelete` 的归属校验代码被整体注释（`FileUploadServiceImpl.java:367-384`）。
- 修复建议：所有文件操作统一走路径校验工具（canonical path + startsWith basepath）；恢复归属校验。

**SEC-11 jasypt 主密钥写在配置文件**
- 位置：`application.yml:30`（`password: smart5c-jasypt-key`）
- 与密文同仓同文件，解密形同虚设。注释已说明生产应 `-D` 覆盖，但 dev/test/kingbase 三份 profile 的数据库/SFTP 密文均可被该默认密钥解开。
- 修复建议：默认密钥从 yml 移除，启动必须注入；或使用 KMS/启动脚本加密。

**SEC-12 越权（IDOR）普遍存在**
- 典型位置：`DataUploadController.fileDelete`（任意 filePath）、`DefectStorageController`（按 id 查改删，无归属校验）、`TaskController` 各接口（任务 id 无归属校验）。`UserInfoServiceImpl.updatePassword` 已校验本人（较好），但 `fileDelete` 的归属校验代码整体被注释（`FileUploadServiceImpl.java:367-384`）。
- 修复建议：对资源型接口补充"创建人/部门"归属校验；启用已有但被注释的校验逻辑。

**SEC-13 依赖版本漏洞**
- 位置：`pom.xml`
  - `spring-boot 2.5.4`（2021 年版本，Spring Framework 5.3.9 内核，受 CVE-2022-22965 Spring4Shell 等影响）；
  - `mysql-connector-java 8.0.21`（CVE-2021-2471 等需 8.0.27+）；
  - `httpclient 4.5.2`（CVE-2020-13956 需 4.5.13+，项目已部分用 4.5.13，存在双版本混用）；
  - `commons-compress 1.19`（解压路径穿越 CVE-2021-36090 系列，项目有 Zip 解压逻辑 `ZipProcessUtil`）；
  - `fastjson2 2.0.23`（早期 2.x，建议升级到 2.0.40+）；
  - `jjwt 0.9.1`（老旧，建议 0.11.5+）。
- 修复建议：升级 Spring Boot 至 2.5.x 最新补丁或 2.7.x LTS，其余按最小修复版本升级。

### 低

**SEC-14 物理 Delete 与逻辑删除策略混用**：`InspectionDataMapper.java:127,130` 使用物理 `@Delete` 删除任务数据，与全局逻辑删除策略不一致，恢复困难。
**SEC-15 `/doc.html` 弱口令**：密码 `123`（同 SEC-09）。
**SEC-16 SFTP 密码经 RSA 加密下发给前端**：前端持有公钥即拥有解密能力，等于明文（同 SEC-02）。
**SEC-17 静态资源白名单过宽**：`/**/*.js`、`/**/*.css` 免鉴权粒度过宽，可能开放非预期路径。

## 二、功能性 Bug

### 高

**BUG-01 `checkProcessError` 卡死检测失效（历史问题复核仍存在）**
- 位置：`schedules/C5Schedule.java:100,107`
- 判断条件 `"0%".equals(entry.getValue())`，而实际写入的进度格式是 `"分析进度：0.00%"`（`InspectionDataServiceImpl.java:564-565`）。`processMap` 中永远不存在裸 `"0%"`（`analysisProcess_` 前缀的初始值 `"0%"` 会在第一轮循环后立即被替换），导致"解析卡死 10 秒自动移除"逻辑**永不生效**，进度条会永久停留在某百分比。
- 叠加问题：`blockMap` 是普通 `HashMap`（`C5Schedule.java:48`），该方法又是 `@Async` + `@Scheduled(fixedRate)` 并发执行，存在并发写坏 Map 的风险。
- 修复建议：进度判断改为解析数值或用数字型进度存储；`processMap`/`blockMap` 换成 `ConcurrentHashMap`；`@Async` 与 `@Scheduled` 不应叠加在同一方法上。

**BUG-02 `refreshToken` 空角色时 IndexOutOfBounds**
- 位置：`service/Impl/UserInfoServiceImpl.java:293-297`
- `roleCodeList = Collections.emptyList()` 后仍执行 `claims.put("roleCode", roleCodeList.get(0))`。用户角色被移除的瞬间触发 token 刷新（`AuthenticationFilter.java:148-150`），将抛 `IndexOutOfBoundsException`，由于过滤器自动刷新，等同于**所有请求 500**。
- 修复建议：空列表时使用默认角色或直接返回 401。

**BUG-03 `AuthenticationFilter` 用户不存在时 NPE 链路**
- 位置：`filter/AuthenticationFilter.java:142-152`
- `userInfoService.getOne(...)` 结果未判空即 `CurrentUserHolder.set(userInfo)`，后续 `MybatisPlusConfig` 的自动填充、`apiUtils.currentUserId()` 等将对 null 解引用。已删除用户持有的有效 token 可触发；也未校验锁定状态（同 SEC-05）。
- 修复建议：`userInfo == null` 或 `lockStatus == LOCKED` 时返回 401。

**BUG-04 首页"最新报警"分页口径错误**
- 位置：`service/Impl/HomePageServiceImpl.java:122-136`、`mapper/InspectionDataMapper.java:70-81`
- `countLatestAlarm` 统计的是**全表记录数**（含非报警数据），而列表查询按 `inspection_time desc limit` 且无 `WHERE` 条件——"最新报警列表"实际是全部数据列表；`total % pageSize == 0 ? 0 : 1` 在 `total=0` 时 pages=1（应为 0），边界不一致。
- 修复建议：count 与 list 条件对齐（加报警状态过滤），或改用 MP 分页插件一次完成。

### 中

**BUG-05 `processMap` 非线程安全且存在内存泄漏**
- 位置：`service/Impl/InspectionDataServiceImpl.java:110`（`public static final Map<String, String> processMap = new HashMap<>()`）
- 被多用户（key 含 userId）、多线程（`@Async taskExecutor` 8 线程 + 定时任务）并发读写；异常路径下 `SOURCE/DEST/SOURCE_SIZE` 三个 key 可能永久残留（`InspectionDataServiceImpl.java:452-456` 复制失败时不清理）。
- 修复建议：改 `ConcurrentHashMap`；用 try/finally 保证清理。

**BUG-06 上传日志查询用错字段**
- 位置：`service/Impl/FileUploadServiceImpl.java:328-329`
- `ge(...startDate)` 正确，但 `le(...)` 的上界也写的是 `getStartDate()` 而非 `getEndDate()`——结束日期过滤失效。
- 修复建议：改为 `query.getEndDate() + " 23:59:59"`。

**BUG-07 `defectStorageDetail` 潜在 NPE 与越界**
- 位置：`service/Impl/DefectStorageServiceImpl.java:258-273`
- `getById(id)` 未判空即 `BeanUtils.copyProperties`；`getImagePath().split("/")` 在路径不足两级时 `pathArr[length-2]` 越界。
- 修复建议：补判空；文件名截取前校验长度。

**BUG-08 分页无上限**
- 位置：各 QO（如 `FileUploadRecordsQO`）均无 `pageSize` 上限校验，可传超大值拖垮内存。
- 修复建议：对 `pageSize` 做上限（如 200）校验。

**BUG-09 `aiAnalysisImage` 吞异常导致状态误置**
- 位置：`InspectionDataServiceImpl.java:1335-1363`
- AI 调用异常仅打日志，外层仍把 `analysisStatus` 更新为 `WAIT_REVIEW`（待审批）——分析失败的数据被当成正常待审数据展示，审批人员无法区分"没分析"和"分析过"。
- 修复建议：异常路径置为独立的"分析失败"状态。

### 低

**BUG-10 `getTwoNumberDivideToPercent` 分母 0 与未开始混同**：`HomePageServiceImpl.java:111-119`，`number1 == 0` 时也返回 0%，无法区分"未开始"和"完成 0 个"，仅影响展示。
**BUG-11 `latestAlarmList` 硬编码 `limit 100`**（`InspectionDataMapper.java:73`）：报表导出最多 100 条，数据量大时静默截断。
**BUG-12 `cleanUnusedRecords` 空表保护仅靠哨兵 `-1L`**：`C5Schedule.java:210-212` 用 `notIn("id", -1L)` 防全删，逻辑成立但脆弱——建议改为"usedIds 为空则直接 return"的防御式写法。

## 三、性能问题

### 高

**PERF-01 首页报警列表全表扫描 + 深分页**
- 位置：`mapper/InspectionDataMapper.java:63-81`
- `order by inspection_time desc limit #{offset},#{pageSize}` 无索引支撑（需确认 `inspection_time` 索引），`count(1)` 每次全表统计；首页轮询调用频繁。
- 优化建议：为 `(inspection_time)` 建索引；count 改为缓存/近似值或游标分页。

**PERF-02 AI 调用串行阻塞 + 超时畸长 + N+1 降级**
- 位置：`TaskServiceImpl.asyncAiCheck`（`TaskServiceImpl.java:570-597`）→ `InspectionDataServiceImpl.processFolderValidation`（`InspectionDataServiceImpl.java:885-919`）；Forest 全局超时 `1000000ms`（约 16.7 分钟，`application.yml:48`）
- 任务线程被长时间占用；一次失败后降级逐子文件夹重试，最坏情况一个文件夹触发 N+1 次完整 AI 调用。
- 优化建议：AI 调用设置独立短超时（如 60s）；降级重试加次数上限与退避。

**PERF-03 图片全量读入内存**
- 位置：`DefectStorageServiceImpl.downloadDefectImage`（`DefectStorageServiceImpl.java:294-305`，`ImageIO.read` 整图 + 重绘 + 写回）；`WaterMarkUtils` 多处 `ImageIO.read`。
- 大图（巡检相机原图可达数十 MB）并发下载时堆内存峰值高，易触发 Full GC。响应未设置 `Content-Length`，也未做 `ClientAbort` 处理。
- 优化建议：无缺陷标注时直接流式拷贝原文件（`Files.copy` 到输出流），仅标注场景走 `ImageIO`。

### 中

**PERF-04 `uploadDataPaging` 假分页：全目录加载后内存过滤**
- 位置：`FileUploadServiceImpl.java:105-141,143-178`
- `folder.listFiles()` 全量载入并排序，`page.setTotal(files.length)` 后**并未按 pageNo/pageSize 截取**，把整目录（含每张图的类型探测、视频时长解析 `getVideoDuration`）全部返回。搜索分支 `searchFilesAndDirs` 还会递归全树。
- 优化建议：分页语义落实到列表截取；视频时长懒加载或缓存。

**PERF-05 `analyzeOrphanInspectionData` 每次全量 list 无分页**
- 位置：`schedules/C5Schedule.java:139-155`
- `wrapper.isNull(taskId)` + 状态过滤后 `list()` 无 limit，积压数据多时一次性载入并逐个触发分析（又叠加 PERF-02），3 分钟一轮，最坏形成任务堆积。
- 优化建议：加 `last("limit N")` 分批消费。

**PERF-06 `detailParseDataOptimized` 单条 insert**
- 位置：`InspectionDataServiceImpl.java:641-642`
- 常量 `BATCH_SIZE = 1000`（`InspectionDataServiceImpl.java:105`）表明本意是批量，但实际每目录 `super.save(inspectionData)` 单条插入；万级目录解析时 insert 次数 = 目录数。
- 优化建议：按 BATCH_SIZE 聚合 `saveBatch`。

**PERF-07 首页统计多次独立 count 查询**
- 位置：`HomePageServiceImpl.todayCheckDataCount`（3 个独立 `@Select`）、`lastWeekAlarmsTrend` —— 每次刷新首页至少 5 次 DB 往返，其中 `sum(image_num)`、`count(distinct ...)` 在大表上均为全扫。
- 优化建议：合并为一条 SQL 或定时预聚合到统计表。

### 低

**PERF-08 `AuthenticationFilter` 每请求两次 DB 查询**：token 解析后 `getOne(account_no)`，token 刷新时再 `refreshToken`（又查一次用户+角色）；可加本地短 TTL 缓存。
**PERF-09 `WebSocketSessionManager.sendMsg` 全局 `synchronized`**（`WebSocketSessionManager.java:27`）：所有会话的发送串行化，一个慢客户端阻塞全部广播；应改为 per-session 锁或并发发送。
**PERF-10 `processMap` 进度串覆盖**：同用户并发解析/分析时进度互相覆盖（key 仅含 userId），显示错乱。
**PERF-11 每请求 info 日志打印 URL+token**：`AuthenticationFilter.java:75,91,101` 高频 info 日志，量大时成为 IO 瓶颈（与 SEC-07 重叠）。

## 四、修复优先级建议

1. **立即（本周）**：SEC-01（命令注入+任意文件删除）、SEC-02（私钥/SFTP 口令下发）、SEC-03（白名单）、BUG-02/BUG-03（登录链路 500/越权）。
2. **短期（两周内）**：SEC-04/05（密码与 JWT 体系）、BUG-01（进度卡死）、PERF-02（AI 调用超时与降级）、SEC-13 依赖升级（Spring Boot、commons-compress、mysql-connector）。
3. **中期（一个月）**：SEC-10 路径校验统一封装、SEC-12 越权治理、PERF-04/05/06（文件与解析批处理）、PERF-01 首页统计优化。

### 5.2 验证结论与严重度调整

1. **SEC-05（JWT 伪造）→ 严重级**。这是全项目最高危问题：不需要密码、不需要有效账号，攻击者仅凭源码（或反编译 jar）中的固定字符串即可伪造任意身份调用**全部**业务接口（含文件删除、数据导出、用户管理）。SEC-10/SEC-01/SEC-02 与之组合形成无鉴权接管链：伪造 token → 遍历文件系统 → 删除任意目录 / 获取 SFTP 口令。
2. **SEC-07（密码哈希回显）→ 高危**。与 SEC-04 组合后，登录响应即泄露可逆的密码哈希，等于密码明文泄露。
3. **SEC-03 降级部分**：actuator/druid 未实际部署，风险消除；但白名单放行 `task/autoCreate` 已通过 405 响应证实（请求穿过了鉴权过滤器）。
4. **动态验证无法覆盖**（需日志/内部权限，本次未验证）：BUG-01 进度卡死（需触发长时间解析）、BUG-02 refreshToken 越界（需清空用户角色，具破坏性）、PERF-02 AI 调用（需 AI 服务配合）、PERF-09 WebSocket 串行化。
